### Fix volumetric shadow heap overflow that crashed the memory pool, and the ASan build
- **Crash**: SIGSEGV in `MemoryPoolSingleBlock::setNextFreeBlock` while playing the ShockWave Nuke General challenge on Linux. The free list of `dmaPool_512` contained 16-bit triangle index data, so some earlier code wrote past its block into the next block's header.
- **Root cause (`W3DVolumetricShadow.cpp`, Generals + GeneralsMD)**: `allocateSilhouette()` sized the silhouette edge list as `numVertices * 5`, but `buildSilhouette()` adds up to 3 edges (6 indices) per polygon, for example for polygons without neighbors (`addNeighborlessEdges()`). Meshes with many open edges overflowed the silhouette. The shadow volume `Geometry` is sized from `m_maxSilhouetteEntries`, so `constructVolume()` also wrote one triangle past the volume index buffer.
- **Fix**: New `silhouetteEntries()` returns `max(numVertices * 5, numPolygons * 6)`, used by `allocateSilhouette()`. `SetGeometry()` now reallocates when the new geometry needs more entries than are allocated (it compared vertex counts with the previous geometry before), and drops the shadow volumes of that mesh so `updateMeshVolume()` allocates them again with the new size.
- **ASan build (`GameMemoryNull.cpp`)**: `sizeof MemoryPoolFactory` without parentheses does not compile with GCC. It is only built with `RTS_GAMEMEMORY_ENABLE=OFF`, for example with `RTS_BUILD_OPTION_ASAN=ON`.
- **`Is_Valid_Float` / `Is_Valid_Double` (`wwmath.h`)**: read the value through an `unsigned long` pointer, which is 8 bytes on 64-bit Linux. ASan reported a stack-buffer-overflow for `Is_Valid_Float`. In `Is_Valid_Double`, the `+ 1` on that pointer moved the read past the double, so it read unrelated memory. Both now `memcpy` the bits into `uint32_t` / `uint64_t`.
- **Validation**: Linux `linux64-deploy` build of `z_generals` with `RTS_BUILD_OPTION_ASAN=ON` and `-fsanitize-recover=address`. Before the fix, ASan reported heap-buffer-overflows in `addSilhouetteIndices`, `constructVolume`, `Geometry::SetPolygonIndex` and `RenderDynamicMeshVolume`. After the fix, the ShockWave Nuke General challenge played to the end on Arch.

### Skip all glibc libraries when bundling Linux runtime libraries
- **Problem**: On Arch Linux, `ldd` reports glibc as `/usr/lib/libc.so.6` and `/usr/lib/libm.so.6`. The `copy_ldd_deps()` skip list only matched multiarch (`/usr/lib/*/`) and `/usr/lib64/` paths, so `libc.so.6` and `libm.so.6` were copied into the runtime directory, but the loader (`/usr/lib64/ld-linux-x86-64.so.2`) was not. Other glibc libraries (`libmvec`, `libresolv`, `libutil`, `libanl`, `libnsl.so.1`, `libnss_*`, `libthread_db` and others) were not in the skip list at all, so they were bundled on every distro when a dependency needed them (for example `libmvec.so.1` via `libx265`).
- **Impact**: With RPATH `$ORIGIN`, the game loads the bundled glibc libraries with the host loader. A glibc update on the host, or another machine, breaks startup until redeploy.
- **Fix**: Added one skip-list line with `/usr/lib/<lib>.so.*` patterns for `libc`, `libm`, `libpthread`, `librt` and `libdl`, and two lines with `*/<lib>` patterns for the remaining glibc libraries, in `deploy-linux-zh.sh`, `deploy-linux.sh`, `bundle-linux-zh.sh`, `bundle-linux.sh`, `build-linux-appimage-zh.sh` and `build-linux-appimage-generals.sh`.
- **Validation**: `bash -n` on all six scripts. Tested the skip patterns against every shared library in the Arch `glibc` package and against Debian/Fedora paths: all versioned glibc runtime libraries and the loader are skipped, non-glibc libraries (`libstdc++`, `libx265`, `libcrypt`, `libnsl.so.2`) are still copied.

### Fix 3D depth test leaks causing missing battleship, sea plane bleed, and occluded object rendering
- **Diagnosed 3D Depth Clipping and Occlusion Bugs (`ShellMapMD.map`)**:
  - Battleship mesh in opening sea scene failed to render, displaying only its dark stencil shadow decal projected on the water.
  - Ocean water plane clipped directly through beach terrain craters and sandbanks, revealing circular dark water patches.
  - Helicopter (Comanche) flying behind the island rendered with its fuselage occluded while its transparent rotor blades rendered in front of the island terrain.
- **Identified Root Causes**:
  1. **Stencil Shadow Depth Function Leak (`W3DVolumetricShadow.cpp`)**:
     - `renderStencilShadows()` explicitly set `m_pDev->SetRenderState(D3DRS_ZFUNC, D3DCMP_ALWAYS)` directly on the hardware device to draw the screen-quad darkening pass across pixels where stencil count was non-zero.
     - Neither `renderStencilShadows()` nor `renderShadows()` restored `D3DRS_ZFUNC = D3DCMP_LESSEQUAL` or `D3DRS_ZWRITEENABLE = TRUE`.
     - Direct hardware calls bypassed `DX8Wrapper`'s shadow render state cache, leaving subsequent draw calls running with `D3DCMP_ALWAYS`.
  2. **Stencil Occluded Player Color Leak (`W3DScene.cpp`)**:
     - In `renderStenciledPlayerColor()`, `DX8Wrapper::Set_DX8_Render_State(D3DRS_ZFUNC, D3DCMP_ALWAYS)` was left at the end of the method without restoring `D3DCMP_LESSEQUAL` and `D3DRS_ZWRITEENABLE = TRUE`.
  3. **Ocean Water Plane Depth Write and Comparison State (`W3DWater.cpp`)**:
     - `drawSea()` executes directly after stencil shadows via `WW3D::Render_And_Clear_Static_Sort_Lists()`.
     - `drawSea()` uses raw vertex/pixel shaders (`m_dwWaveVertexShader`, `m_dwWavePixelShader`) with `D3DRS_ZWRITEENABLE = FALSE` and never enforced `D3DRS_ZFUNC`. With `D3DRS_ZFUNC` leaking `D3DCMP_ALWAYS`, the entire sea plane passed depth testing unconditionally and overwrote the previously drawn battleship opaque geometry, as well as terrain depressions.
  4. **Post-Processing & Frame Initialization Baseline (`W3DPostProcess.cpp`, `ww3d.cpp`)**:
     - `W3DPostProcess::beginScene()` clears scene color and depth/stencil buffers, but did not guarantee restoring `D3DRS_ZENABLE`, `D3DRS_ZWRITEENABLE`, and `D3DRS_ZFUNC = D3DCMP_LESSEQUAL` after target redirection.

### Fix black screen on macOS caused by D3D render state leak in projected terrain shadows
- **Diagnosed Black Screen on macOS Startup**: Following commits `c6728864c` and `f5f331678`, launching Zero Hour or Generals base game on macOS resulted in a completely black screen. Audio played, mouse clicks and cursor movement were processed, and window managers received inputs, but all visual presentation remained solid black.
- **Identified Root Causes**:
  1. **Direct D3D8 Render State Leak in `renderProjectedTerrainShadow` (`W3DProjectedShadow.cpp`)**:
     - In `c6728864c`, `W3DProjectedShadowManager::renderShadows` was updated from `if (shadow->m_type == SHADOW_PROJECTION)` to bitwise `if (shadow->m_type & SHADOW_PROJECTION)`. Dynamic projected shadows (`SHADOW_DYNAMIC_PROJECTION | SHADOW_PROJECTION = 0x0C`) previously evaluated to `FALSE` in retail Zero Hour, skipping `renderProjectedTerrainShadow()`.
     - With bitwise execution enabled, `renderProjectedTerrainShadow()` executed every frame during `drawViews()`. Inside this method, `m_pDev->SetRenderState(D3DRS_SRCBLEND, D3DBLEND_DESTCOLOR)` and `m_pDev->SetRenderState(D3DRS_DESTBLEND, D3DBLEND_ZERO)` were set directly on the Direct3D device, bypassing `DX8Wrapper`'s cached state tracking and never restoring previous blend modes.
     - Additionally, `projector->Peek_Material_Pass()->Install_Materials()` enabled `D3DRS_ALPHABLENDENABLE = TRUE` while `UnInstall_Materials()` was an empty stub (`{}`).
     - Subsequent draw calls (opaque meshes in `TheDX8MeshRenderer.Flush()`, trees, translucent meshes, post-processing, and 2D UI in `TheWindowManager->draw()`) operated with multiplicative blending ($\text{Color} = \text{Src} \times \text{Dst} + 0$) against the cleared black backbuffer/scene target ($(0, 0, 0)$), multiplying all pixels by zero and rendering every 3D object, UI layout, text element, and mouse cursor 100% pitch black.
  2. **Render Target Depth Buffer Fallback Failure in `dx8wrapper.cpp`**:
     - `DX8Wrapper::Create_Render_Target` unconditionally failed and returned `*target = nullptr` if the hardware did not support depth-stencil texturing (`Support_Depth_Stencil_Format`), which occurs on Apple Silicon MoltenVK.
     - Resolved by allowing the color render target texture to be created even when depth texturing is unavailable, returning `*depth_buffer = nullptr` for safe handling in `Set_Render_Target_With_Z`.
  3. **`IsRenderToTexture` State Corruption in `dx8wrapper.cpp`**:
     - In `DX8Wrapper::Set_Render_Target(IDirect3DSurface8* render_target, IDirect3DSurface8* depth_buffer)`, restoring the default backbuffer (`render_target == nullptr || render_target == DefaultRenderTarget`) unconditionally executed `IsRenderToTexture = true` at the exit of the function, corrupting the RTT state machine. Fixed to set `IsRenderToTexture = false` when restoring the default target.
- **Implemented Fixes**:
  - Saved and restored all D3D render states (`D3DRS_ALPHATESTENABLE`, `D3DRS_STENCILENABLE`, `D3DRS_STENCILPASS/FAIL/ZFAIL`, `D3DRS_STENCILFUNC`, `D3DRS_STENCILREF`, `D3DRS_STENCILMASK`, `D3DRS_STENCILWRITEMASK`, `D3DRS_LIGHTING`, `D3DRS_SRCBLEND`, `D3DRS_DESTBLEND`, `D3DRS_ALPHABLENDENABLE`) in `renderProjectedTerrainShadow()`.
  - Injected `DX8Wrapper::Invalidate_Cached_Render_States()` and `ShaderClass::Invalidate()` upon exit of `renderProjectedTerrainShadow()` and at the conclusion of projector material passes in `renderShadows()`.
  - Maintained 1:1 parity between `GeneralsMD` (Zero Hour) and `Generals` base game.
  - Verified clean native compilation on macOS ARM64 (`macos-vulkan`) and verified process lifecycle execution.

### Fix macOS fullscreen black screen loop caused by DXVK swapchain reset failure
- **Diagnosed Black Screen in Fullscreen Mode on macOS**:
  - Investigated execution logs (`logs/run_zh_macos.log`) and verified using downloaded macOS release artifact (`GeneralsXZH.app`).
  - While windowed mode (`-win`) rendered properly, fullscreen mode on macOS consistently resulted in a solid black screen while audio played and mouse clicks registered.
- **Identified Root Causes**:
  1. **Asynchronous Cocoa Fullscreen Window Resizing**:
     - On macOS, SDL3 creates the window before the Cocoa asynchronous fullscreen animation finishes, initializing D3D8 swapchain backbuffer dimensions to an intermediate size (e.g., `2048x1536`).
     - On the next frame, Cocoa completes the transition and reports the native Retina physical resolution (`2880x1800`), causing `Pillarbox_Process_Resize()` to detect a dimension mismatch and trigger `DX8Wrapper::Reset_Device()`.
  2. **DXVK Strict Losable Resource Accounting in D3D8 Emulation**:
     - DXVK emulates D3D8 on top of its D3D9 layer. By default, `d3d9.countLosableResources = True`.
     - When `Reset_Device()` called `m_pDev->Reset()`, DXVK rejected the swapchain recreation because alive `D3DPOOL_DEFAULT` subresources remained referenced:
       `warn: Device reset failed because device still has alive losable resources: Device not reset. Remaining resources: 1`
     - Windows Direct3D 8 did not enforce strict losable resource accounting during `Reset()`. DXVK's reset failure placed the device into a permanent `D3D9DeviceLostState::NotReset` state.
     - As a consequence, every subsequent `Present()` call failed with `D3DERR_DEVICELOST`, causing the game engine to attempt another `Reset_Device()` on every single frame in an infinite loop, never rendering any visual frames.
  3. **Pillarbox Offscreen RT and Shadow Resource Leaks Across Device Resets**:
     - `Pillarbox_Setup()` creates offscreen color surfaces and depth-stencil surfaces in `D3DPOOL_DEFAULT` which were not released prior to `Reset_Device()`.
     - `W3DShadowManager` held texture render targets without hooking into `DX8_CleanupHook`.
- **Implemented Fixes**:
  - **DXVK Configuration**: Set `d3d9.countLosableResources = False` in `resources/dxvk/dxvk.conf` to mirror standard DXVK behavior for legacy D3D8 games where strict resource accounting prevents swapchain resizing.
  - **Unbind Custom Render Targets**: Restored default render targets and depth buffer (`Set_Render_Target(static_cast<IDirect3DSurface8*>(nullptr))`) before calling `Reset()` in `DX8Wrapper::Reset_Device()`.
  - **Pillarbox Surface Management**: Added `Pillarbox_Cleanup()` prior to device reset and re-initialized `Pillarbox_Setup(ResolutionWidth, ResolutionHeight)` after successful reset in `dx8wrapper.cpp`.
  - **Shadow Manager Reset Hook**: Registered `W3DShadowManager` as a `DX8_CleanupHook` via `DX8Wrapper::AddCleanupHook(this)` and `DX8Wrapper::RemoveCleanupHook(this)`, with `ReleaseResources()` and `ReAcquireResources()` implemented across both `GeneralsMD` (Zero Hour) and `Generals` base game.
  - **Local Verification**: Verified on macOS Apple Silicon that device reset succeeds cleanly, swapchain resizes to `2880x1800` physical Retina pixels, and fullscreen rendering presents perfectly with zero frame drops or reset loops.

### Fix critical sections staying locked after nested use (CompatLib)
- `LeaveCriticalSection` in both `threads_compat.h` copies only unlocked the pthread mutex when the depth counter reached 0, but the mutex is recursive and `EnterCriticalSection` locks it on every enter. After any nested enter/leave the owning thread kept the mutex forever, so a second thread entering the same critical section (memory pools, DMA) blocked for good. This is what made the background audio decode hang.
- Leave now always unlocks and only clears the owner at depth 0. Confirmed with a standalone test: nested enter/leave on one thread, then another thread enters; it blocked before and gets the lock now. Single-threaded behaviour is unchanged.

### Fix water rendering and missing ships on Windows (macOS parity and D3D8 depth leaks)
- **Diagnosed Windows Shellmap Water & Ship Disappearance**: On Zero Hour's `ShellMapMD.map` under Windows, water was completely invisible/missing, showing the raw stone seabed underneath, and ships (battleships, carriers) failed to render. macOS functioned 100% perfectly.
- **Identified Root Causes**:
  1. **Legacy Runtime Assembler Shaders Divergence (`W3DWater.cpp`)**: Under `#ifdef _WIN32`, legacy 2002 runtime pixel shaders (`m_trapezoidWaterPixelShader`, `m_riverWaterPixelShader`, `m_waterPixelShader`) were compiled via `D3DXAssembleShader`. On macOS and Linux, these shaders were never compiled (remaining `nullptr`), so macOS used the clean, fixed-function pipeline with `_PresetAlphaShader` and the precompiled `m_reflectionPixelShader`. On Windows, `m_trapezoidWaterPixelShader` produced broken alpha output during destination-alpha soft edge feathering (`D3DBLEND_DESTALPHA`), leaving water polygons transparent.
  2. **Global Depth Test Leak (`D3DRS_ZFUNC = D3DCMP_EQUAL`)**: In `drawTrapezoidWater()`, shroud passes explicitly called `SetRenderState(D3DRS_ZFUNC, D3DCMP_EQUAL)` without restoring `D3DCMP_LESSEQUAL`. Because `D3DRS_ZFUNC` remained `D3DCMP_EQUAL`, all subsequent water polygons, translucent meshes, particles, and ship models in subsequent frames were tested for exact equality against the cleared (1.0) depth buffer and were completely discarded by the GPU.
  3. **Reflection Render Target Depth Buffer Dimension Mismatch (`dx8wrapper.cpp`, `W3DWater.cpp`)**: `m_pReflectionTexture` (512x512) was created without a matching depth-stencil buffer. When `renderMirror()` called `Set_Render_Target_With_Z`, `DX8Wrapper` attempted to pair the 512x512 texture with `DefaultDepthBuffer` (e.g. 1920x1080), which native Direct3D 8 strictly rejects (`D3DERR_INVALIDCALL`), failing offscreen redirection and corrupting backbuffer rendering.
- **Implemented Fixes**:
  - Aligned Windows with macOS: Disabled runtime `#ifdef _WIN32` shader assembly in `ReAcquireResources()`, ensuring all platforms use the reference fixed-function pipeline (`_PresetAlphaShader`) and precompiled reflection bytecode.
  - Fixed depth compare leaks in `drawTrapezoidWater()` and `drawRiverWater()`: Removed `D3DCMP_EQUAL` leaks, restored `D3DCMP_LESSEQUAL`, and called `ShaderClass::Invalidate()` to ensure render state synchronization across all draw calls.
  - Allocated dedicated matching depth buffer `m_pReflectionZTexture` via `DX8Wrapper::Create_Render_Target()` with `WW3D_ZFORMAT_UNKNOWN` (resolving auto depth format with 16-bit fallback) and passed it to `Set_Render_Target_With_Z()`.
  - Prevented binding mismatched `DefaultDepthBuffer` when no custom Z texture is supplied in `DX8Wrapper::Set_Render_Target_With_Z()`.
- Verified 100% clean builds for both Zero Hour (`GeneralsXZH`) and Generals base game (`GeneralsX`) via Docker (`linux64-deploy`).

When `m_numTreeTypes == 0`, returning `0` caused `addTree()` to accept `treeType = 0` as valid while leaving `m_treeTypes[0].m_data` uninitialized (null) and registering the tree into the spatial partition `m_areaPartition`.
- Corrected `addTreeType()` to return `-1` on error and guarded `addTree()` against null data pointers.
- Added comprehensive bounds checks (`treeType >= 0 && treeType < m_numTreeTypes`) and null guards for `m_data` across `unitMoved()`, `pushAsideTree()`, `applyTopplingForce()`, `updateTopplingTree()`, `update()`, `updateTreeBuffers()`, and `xfer()`.
